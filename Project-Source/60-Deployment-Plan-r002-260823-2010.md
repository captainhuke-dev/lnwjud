# 60 — Deployment Plan

## Deployment Scope
Current verified installation/operation model for lnwjud plus approved planned operational contracts for recovery, rolling upstream adoption and remote control. Planned procedures are not currently implemented capabilities and do not authorize operational mutation by themselves.

## Existing Deployment Support
`SOURCE_ONLY` as the current source-governance classification. The repository produces Windows installer/runtime artifacts; no Docker deployment mode is established by current evidence.

## Common Prerequisites / Boundaries
Windows x64; compatible permissions; for source development Node.js `>=24 <25` and pnpm `10.15.0`; network access where Secure MCP Tunnel, updates or remote Git are used. Runtime secrets remain outside Git/Project Source. Runtime state authority is separate from Project file-storage binding.

## Existing Verification / Diagnostics Contract
Use repository-targeted lint/typecheck/tests/build/release gates appropriate to changed scope. Runtime connection health must be verified from current local endpoint/tunnel state when an operational task requires it. Desktop Live Logs/Work Log, audit metadata, doctor/health surfaces and relevant Windows/runtime logs are diagnostic sources.

## Planned Recovery Operations — ACT-LNW-001
A future out-of-band mechanism should expose the following governed escalation model:

### Level 1 — Soft Recovery
Health → probe/wake → reconnect → verify.

### Level 2 — Engine Recovery
Stop bounded affected component → verify stale-process ownership/state → start → health verification.

### Level 3 — Diagnostic Recovery
Collect bounded logs/process/port/tunnel/session evidence → classify root cause → apply only authorized repair → restart affected component → verify machine reachability, engine/MCP/tunnel/tool-discovery/test-command signals.

### Level 4 — Human Approval
Material destructive/system-wide actions require explicit current approval/authority before execution. Examples include destructive Git/data repair, source/config deletion, force operations or system restart where material.

This is an operational contract, not proof an out-of-band path already exists.

## Planned Rolling Upstream Application Upgrade — ACT-LNW-002
Application-upgrade flow (distinct from ProjectFramework upgrade):
```text
Fresh Git observation
→ classify local/remote/base/WIP state
→ identify prior upstream + prior custom intent + new upstream
→ classify customization deltas
→ drop upstream-resolved/obsolete intent
→ forward-port still-valid intent in governed workspace
→ affected verification
→ regression verification
→ fresh base/acceptance check
→ stable promotion
→ rollback evidence
```

Do not create branch/worktree, merge, rebase, fetch, push or apply patches under this planning revision alone. `ISS-002` and current base divergence must be resolved/classified first.

Minimum regression intent from the approved handoff includes engine lifecycle, MCP, tunnel/session, tool discovery, Windows integration and recovery fallback flows as applicable to the eventual changed scope; exact test commands must be derived from then-current repository truth.

## Planned Remote Operational Classes — ACT-LNW-004
- **Normal:** health/status/logs and bounded start/stop/restart/tunnel reconnect.
- **Diagnostics:** processes, ports, configuration state, MCP/tunnel/Codex/Git diagnostics as authorized.
- **Recovery:** stale-process handling, affected engine/tunnel restart, approved recovery procedure, Codex-assisted diagnosis/repair fallback where separately authorized.
- **High Risk:** rollback, system/config mutation, reboot, destructive Git/data actions or equivalent shared/irreversible effects; require explicit governed approval.

Remote connectivity must not be treated as authority. Audit/evidence expectations apply to action execution.

## Persistent Task Bridge Operations — ACT-LNW-003
This intake does not define a deployment/runbook for the Task Bridge. Operational procedures will be materialized only after the action selects its persistence authority/storage/runtime design and receives implementation scope.

## Existing Upgrade / Rollback / Backup
Application upgrades continue to follow repository/release architecture and current release instructions until `ACT-LNW-002` changes are implemented and accepted. Framework upgrades remain separately governed by `FRAMEWORK-001` and `16`. Rollback/backup/restore must preserve verified persistent-state compatibility and destructive authority boundaries.

## Known Limitations / Deployment Mode Variance
Secure Tunnel, stdio and loopback HTTP have distinct runtime boundaries. Planned Supervisor/Web/Task-Bridge capabilities are not yet current runtime truth.
