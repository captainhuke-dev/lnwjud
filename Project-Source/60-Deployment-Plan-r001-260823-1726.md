# 60 — Deployment Plan

## Deployment Scope
Current verified installation/operation model for lnwjud Desktop, local stdio MCP and OpenAI Secure MCP Tunnel. This document records existing repository truth; it does not authorize deployment mutation by itself.

## Deployment Support
`SOURCE_ONLY` as the current source-governance classification. The repository also produces Windows installer/runtime artifacts; no Docker deployment mode is established by current evidence.

## Common Prerequisites
Windows x64; compatible permissions; for source development Node.js `>=24 <25` and pnpm `10.15.0`; network access where Secure MCP Tunnel, updates or remote Git are used.

## Configuration / Secret References
Permission profile, Strict Roots and user/runtime configuration are runtime settings. Secure MCP Tunnel/API credentials remain outside Git and Project Source; runtime storage may use Windows DPAPI as documented by the application.

## Deployment Source / Artifact Acquisition
Canonical implementation source is `captainhuke-dev/lnwjud`. Published Windows installer/runtime artifacts are derived release outputs; exact artifact identity must be freshly verified for a deployment task.

## Source-to-Runtime Mapping
Source development uses build/direct execution from the bound workspace. Packaged Desktop and stdio/Secure-Tunnel launcher are built/packaged artifacts derived from repository source.

## Runtime Mutability Expectation
Runtime local configuration, logs, SQLite state, durable background-task state and caches may change without modifying canonical source. Runtime-only mutation never becomes Implementation Truth automatically.

## Persistent-State Boundary
State required to survive expected runtime restart/replacement includes application-managed persisted settings/task/audit/backup data according to existing runtime implementation. Exact paths/owners must be verified from current code/config before destructive operational work.

## Data / Storage Authority
Runtime persistent data authority is separate from Project File Storage Binding. No generic external Project file storage is bound at bootstrap; Google Drive is unresolved.

## Replacement / Recreation Expectation
Packaged application/runtime binaries are recreatable from accepted source/release artifacts. User/runtime data that must survive replacement follows the application's persisted-state/backup contract and must not be deleted without explicit authority.

## Development-only vs Production Mapping Differences
Development uses source workspace/toolchain; end-user deployment uses packaged Windows artifacts and bundled runtime components. Material differences must be verified per release.

## Source Installation View
Repository README/package scripts are the current operational reference for source dependencies, build, desktop start, tests, packaging and release verification. Commands must be freshly verified before execution when material.

## Docker Installation View
`NOT_APPLICABLE` based on current inspected repository evidence.

## Verification / Health
Use repository-targeted lint/typecheck/tests/build/release gates appropriate to changed scope. Runtime connection health must be verified from the active local endpoint/tunnel state when a deployment task requires it.

## Logs / Diagnostics
Desktop Live Logs/Work Log, audit metadata, doctor/health surfaces and relevant Windows/runtime logs are diagnostic sources as documented by the repository.

## Upgrade
Application upgrades follow repository/release architecture and current release instructions. Framework upgrades are separately governed by `FRAMEWORK-001` and `16`.

## Rollback
Use source/release rollback mechanisms appropriate to the affected component and preserve persistent-state compatibility. Never infer destructive rollback authority from this plan.

## Backup / Restore
The README documents SQLite-consistent backup/restore for application-managed state. Exact current behavior and paths must be verified before operational use.

## Uninstall / Cleanup
Requires explicit task scope and destructive-operation authority; preserve user/runtime data according to verified retention requirements.

## Troubleshooting

## Known Limitations / Deployment Mode Variance
