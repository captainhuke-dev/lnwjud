# 06 — Architecture

## Architecture Scope
High-level architecture of the existing lnwjud Windows-first MCP gateway and desktop runtime.

## Components
- `apps/desktop` — Electron control center and local runtime orchestration.
- `apps/cli` — command-line surface.
- `packages/mcp-server` — MCP protocol/tool gateway.
- `packages/workspace`, `filesystem`, `git`, `process`, `storage`, `permissions`, `audit`, `codex`, `capabilities`, `application`, `domain`, `ipc-contracts`, `project`, `search`, `shared`, `extensions` — modular capability layers.
- `native/windows-ocr` and packaged Windows helpers — native capability boundary.

## Interfaces
MCP stdio, loopback Streamable HTTP, OpenAI Secure MCP Tunnel, Electron IPC, Windows APIs/COM, WSL execution boundary, Git/filesystem/process interfaces.

## Data Flow
AI/MCP client → MCP gateway/policy → scoped capability backend → Windows/local resource → bounded/redacted result → client. Durable task and audit/storage state persist locally where configured by the runtime.

## Dependencies
Windows x64; Node.js 24.x; pnpm workspace; Electron; Vite; TypeScript; optional platform/native providers as documented in repository sources.

## Security / Authority Boundaries
Permission profiles and explicit-confirmation gates govern destructive operations. Project Source authority remains separate from runtime capability availability. Secrets remain external.

## Runtime / Deployment Boundaries
Desktop runtime, stdio/Secure-Tunnel launcher and loopback HTTP are distinct connection surfaces. Current workspace path is local routing evidence governed by `FRAMEWORK-001`.

## Key Architecture Decisions
See repository architecture docs plus `DEC-001` and `DEC-002` for Project Source adoption/routing decisions.

## Known Constraints
Windows-first implementation; current repository contains pre-existing uncommitted implementation work; external Drive/storage authority is unresolved unless later bound.
